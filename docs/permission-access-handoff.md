# من ساسكي إلى لوفي وناروتو — الصلاحيات والوصول

فرع `avg-sasuke`، مبني على أحدث avg عند `46fa71d5` (يشمل عقد `9920e7c6`). واجهة فقط؛ ما لمست الباك إند أو الترحيلات.

## المكتمل

- `/permissions` ونفس الشاشة المضمّنة بإدارة الموظفين: تبويبا «صلاحيات الموظف» و«مطابقة الصنف».
- كتالوگ الخادم هو مصدر المجموعات والأسماء والحزم والأقفال. بحث بالصلاحيات والمجموعات وأسماء الوكلاء، عدّادات، ومفاتيح مستقلة.
- الحزمة تمنح القابل للمنح فقط. إطفاء فرع يطفي مفتاح الحزمة بالمسوّدة حتى لا تبقى الحزمة تمنحه ضمنياً. درجات عروض الأسعار تبقى متبادلة، بمجموعة مستقلة، مثل الواجهة السابقة.
- مصدر الصلاحية وسبب الاستثناء ومدة الانتهاء ظاهرة. المسوّدة ما تنرسل إلا من مراجعة الفروق وكتابة السبب والتأكيد. الحفظ delta وليس استبدال القائمة. رقم النسخة من الخادم كما هو.
- 409 يوقف الحفظ والمفاتيح لحد تحديث صريح يلغي المسوّدة. حراسة alive لجلب الموظف والقائمة والسجل، وحراسة التبديل مع مسوّدة غير محفوظة. فشل الجلب لا يُفسّر كقائمة صلاحيات فارغة.
- مراجعة استثناء/صلاحية مؤقتة (بغداد → RFC3339)، مع الحفاظ على السبب والموعد الحاليين عند تعديلها، وتأكيد إزالة **تثبيت الاستثناء فقط** مع توضيح أن الصلاحية تبقى. سجل التغييرات مع أسبابها والفاعل والوقت.
- الوكلاء: توجيه ماتركس/الجودة/الحجوزات، وايريس مقفولة للمالك + ADMIN بدون مفتاح. التسمية حسب `editable` الفعلي: ماتركس وايريس ثابتان بالخادم، الجودة والحجوزات قابلان للتسمية للمالك. لا نغيّر التشغيل العام للوكلاء من هذه الشاشة.
- لأن GET أسماء الوكلاء خاص بالمالك، ADMIN لا يناديه إطلاقاً ويشوف أسماء وظيفية عامة للجودة والحجوزات. حتى يشوف الأسماء المخصصة يحتاج GET آمن مسموح له من لوفي، وليس تجاوز الحارس.
- المطابقة: ملخص مطابق/اختلاف/بلا قالب، بحث، عرض الإضافات والإزالات والاستثناءات والمقفول، سبب وتأكيد قبل POST. بلا قالب لا يوجد تنفيذ. لو بقي اختلاف بالخادم، ما نعرض نجاح «مطابق» كاذب.
- حفظ مكوّن نطاق إدارة الموظفين السابق عند الصلاحيات المعنية، وحارس الصفحة حتى بالوضع المضمّن. تعديل صلاحيات حساب ADMIN/OWNER مقفول أمام ADMIN مثل الخادم.
- نمط ليلي عبر متغيرات index.css المركزية، حقول 16px، مفاتيح لها أسماء وحالة قارئ الشاشة، ونوافذ بحصر التركيز وإرجاعه وEscape. أخطاء API تبقى بنفس الرسائل؛ أضفت ApiError.status حتى نميّز 409 بدون تخمين نصه.

## الفحص

نجحت tsc وeslint وbuild وdiff check. متصفح Chromium على Vite ببيانات اصطناعية، بعرض 390 و1366 والوضع الليلي:

- الحزمة والاختيار الجزئي، مسوّدة بلا طلب PUT قبل التأكيد، حفظ add/remove/version، والتحذير عند تبديل الموظف.
- 409 متعمد، قفل إعادة الحفظ، ثم تحديث. فشل GET لا يسمح بتعديل أو حفظ، وجواب موظف متأخر لا يطمس الموظف المختار.
- استثناء مؤقت وتحويل موعد بغداد إلى UTC، وإزالة التثبيت بدون حذف الصلاحية، وقفل ايريس، وتسمية وكيل للمالك.
- معاينة المطابقة ثم تأكيدها، وبلا قالب لا زر تنفيذ، وحالة اختلاف باقٍ لا تُعلن «مطابق».
- حساب ADMIN: المفاتيح المقفولة وحساب المدير للعرض فقط، **ولا طلب لمسارات المالك**. موظف غير مخوّل: **صفر طلبات API** من الشاشة.
- بحث ايريس، وتبادلية درجات عروض الأسعار، وعدم تجاوز عرض الموبايل.
- تباين نص البطاقة والنص الثانوي فوق 4.5:1 في النهاري والليلي، مقاس من ألوان المتصفح الفعلية.

إعادة الفحص مع Vite شغال:

```sh
PLAYWRIGHT_MODULE=/path/to/playwright node scripts/check-permission-access.cjs
```

اختياري: ACCESS_BASE_URL وCHROMIUM_PATH. المعاينة تركّب مكوّن الشاشة ببيانات جلسة وهمية وتعترض API بالكامل؛ **ليست فحصاً حيّاً لقاعدة البيانات**. الصور الاصطناعية في `docs/permission-access-previews/`.

## ملاحظات خادم للوڤي قبل الترقية

1. `RemoveException` بالعقد الحالي لا يستقبل version، ولا يطبّق lockFor/قفل حسابات الإدارة، ولا يزيد accessVersion أو يسجل إزالة التثبيت. الواجهة تقفل هذه الحالات حسب الكتالوگ والدور، لكن هذا ليس بديلاً عن حراسة الخادم. نحتاج اتفاق عقد لنسخة وتدقيق العملية قبل ادعاء حماية تزامنها مثل الحفظ والمطابقة.
2. `AddException` ينفّذ apply ويثبت منح الصلاحية/version أولاً، ثم يكتب PermissionException خارج المعاملة؛ فشل الكتابة الثانية ممكن يرجّع خطأ مع بقاء المنح. يفضّل جمعهما بمعاملة واحدة. ما سوّيت retry آلي من الواجهة.
3. أسماء كل الوكلاء ليست قابلة للتعديل حالياً، وGET الأسماء للمالك فقط؛ السلوك أعلاه مقصود حسب الحارس الفعلي، وليس مساراً مخمناً.

المتبقي: فحص لوفي/ناروتو بعقد وقاعدة حيّين وحسابي OWNER وADMIN، خصوصاً سباق النسخ والاستثناءات وأثر الحزم الحقيقي، ثم الدمج. لا رفع على prod. ظهور التعديل بالسيرفر يحتاج نشر وبناء بعد الموافقة.

# (ع) → (م) و(ز): رؤية «المراقب الحي» ومحرك القصص

هذه الوثيقة توسّع `02-decision.md`. المطلوب النهائي **ليس صورة Avatar متحركة
ولا Widget للتنبيهات**؛ المطلوب كيان رقمي يعيش داخل النظام، يتابع أحداثه
الموثوقة، ينفذ مشاهد مترابطة بين واجهات المستخدمين، يتكلم ويتفاعل ويتذكر أين
وصلت كل رسالة.

Rive هو **جسد الكيان وتعابيره** فقط. العقل، الحدث، القصة، التوصيل والحفظ تبقى
في كود النظام والخادم.

## 1. الشخصيتان

### أفتار الموظف

- يتولد من صورة الموظف ويحافظ على ملامحه الأساسية.
- يلبس سترة الأماني الزرقاء فوق ملابس سوداء.
- يستلم الرسائل، يقرأ، يتفاعل، وينقل معناها للموظف.

### مراقب الموظف

- كيان مرافق له شخصية واضحة، حاضر في واجهته ويتابع الأحداث المسموح بها.
- يلفت نظره إلى النقص والخطأ والموعد والإنجاز.
- لا يملك صلاحية اختراع إجراء إداري؛ يعرض نتيجة حدث رسمي صادر من النظام.

الفصل البصري بين الاثنين يمنع خلط الموظف بالجهة التي تراقبه. يمكن استعمال
Master Rig مشترك مع اختلافات واضحة بالملابس/الشارة/الدور، لكنهما actorان
مستقلان داخل القصة.

## 2. السيناريو المرجعي: خصم نقطة

هذا السيناريو هو **اختبار قبول معماري**، وليس مؤثراً شكلياً:

1. المراقب البشري يضغط «خصم نقطة» لموظف محدد.
2. الخادم يتحقق من الصلاحية ويسجل الخصم أولاً؛ الحركة لا تسبق نجاح العملية.
3. ينشئ النظام حدثاً موثوقاً `DISCIPLINE_POINT_DEDUCTED` بمعرّف idempotency.
4. تنشأ مهمة قصة مرتبطة بالمراقب والموظف المستهدف، ولا تحتوي بيانات أكثر مما
   يحتاجه الطرفان.
5. في واجهة المراقب: يصل مستند بصري للشخصية، تمسكه، تركض نحو حافة الشاشة
   وتخرج. هذه مرحلة `DISPATCHED` وليست دليلاً أن الموظف شاهده.
6. الخادم يوصل الحدث إلى جلسة الموظف. إذا كان غير متصل تبقى المهمة محفوظة.
7. عند وصول/دخول الموظف: تدخل شخصية المراقب من الحافة حاملة المستند.
8. تسلّم المستند إلى أفتار الموظف؛ الأفتار يفتحه ويقرأه.
9. يتغير التعبير إلى التحذير وتظهر فقاعة React عربية: «انخصمت منك نقطة»
   والسبب والتاريخ وزر «عرض التفاصيل».
10. نسجل الحالات منفصلة: وصل للجهاز، عُرض المشهد، فتح التفاصيل، وأقر الموظف
    بالاطلاع. لا نعدّ الخروج من شاشة المراقب «قراءة».
11. إذا انقطع الاتصال وسط المشهد، يستأنف من checkpoint آمن أو يعرض نسخة
    مختصرة؛ لا يتكرر الخصم ولا تضيع الرسالة.

## 3. الحقيقة التقنية للانتقال بين الواجهات

الشخصية لا تنتقل مادياً بين جهازين. الخادم يحفظ **حدثاً واحداً وقصة ذات مراحل**،
وكل واجهة تعرض فصلها الخاص. التطابق بالـevent ID والتوقيت يجعل التجربة تبدو
كأن الشخصية خرجت من جهاز المراقب ودخلت جهاز الموظف.

```text
إجراء رسمي
  → Domain Event
  → Story Instance + Audience
  → Scene Queue لكل واجهة
  → Rive actions + React overlays
  → Delivery / Seen / Opened / Acknowledged
```

## 4. قاموس أفعال قابل للتركيب

لا نبرمج كل فكرة كصفحة مستقلة. نبني أفعالاً صغيرة تُركب منها آلاف القصص:

- `ENTER_FROM_EDGE`
- `WALK_TO_TARGET`
- `RUN_TO_EDGE`
- `EXIT_TO_RECIPIENT`
- `PICK_UP_DOCUMENT`
- `CARRY_DOCUMENT`
- `DELIVER_DOCUMENT`
- `OPEN_DOCUMENT`
- `READ_DOCUMENT`
- `POINT_AT_UI`
- `SPEAK`
- `WAIT_FOR_ACK`
- `CELEBRATE`
- `SHOW_WARNING`
- `RETURN_TO_IDLE`

كل action له: actor، target، مدة، animation name، payload آمن، fallback،
وcheckpoint. النص والورقة والأزرار يرسمها React، والحركة الجسدية Rive.

## 5. نموذج القصة المقترح

```ts
type StoryInstance = {
  id: string
  eventId: string
  storyType: string
  version: number
  senderEmployeeId?: string
  recipientEmployeeId: string
  status: 'QUEUED' | 'DELIVERED' | 'PLAYING' | 'SEEN' | 'OPENED' | 'ACKNOWLEDGED' | 'FAILED'
  currentStep: number
  createdAt: string
  expiresAt?: string
  payload: Record<string, unknown>
}
```

هذا عقد مبدئي للنقاش، وليس تصريحاً بإنشاء الجدول قبل مراجعة الموجود فعلياً
بالنظام؛ نعيد استعمال notification/audit infrastructure حيث يصلح.

## 6. مصادر الأحداث الأولى

- خصم نقطة أو إرجاعها.
- نقص ورقة أو حقل مطلوب في الحجز.
- تأخير مهمة أو قرب موعد.
- إكمال تقرير/فاتورة/عمل.
- رسالة إدارية موجهة.
- مهمة ميدانية جديدة.
- مدح أو إنجاز موثوق.

كل قصة تبدأ من حدث حقيقي. لا ينشئ الذكاء خصماً أو عقوبة أو حقيقة إدارية، ولا
يغير نتيجة مسجلة. يمكنه صياغة شرح مساعد فقط مع fallback نصي ثابت ومراجع.

## 7. التوصيل والاعتمادية

- قناة فورية SSE أو WebSocket للتنبيه، لكن قاعدة البيانات هي مصدر الحقيقة.
- Inbox دائم حتى لا تضيع القصة عند غياب الموظف.
- idempotency تمنع تكرار الحدث أو تنفيذ الأثر الإداري مرتين.
- ترتيب وأولوية: العقوبات/الأمان قبل الاحتفال؛ لا تعمل قصتان جسديتان معاً.
- deduplication وتجميع التنبيهات المتشابهة حتى لا يصبح الكيان مزعجاً.
- fallback نصي كامل إذا فشل Rive أو فُعل reduced motion.
- تسجيل audit للحالة دون تسجيل حركات العين والمؤشر كبيانات حساسة.

## 8. الخصوصية والصلاحيات

- الكيان لا «يراقب كل شيء» بمعنى وصول شامل؛ يرى فقط الأحداث التي يحق لذلك
  الموظف رؤيتها حسب الخادم.
- لا نعتمد إخفاء الصفحة أو الحركة كحماية.
- payload المستلم لا يتضمن أسراراً أو بيانات موظف آخر بلا حاجة.
- صورة الموظف الأصلية لا تدخل ملف `.riv` ولا تُرسل لمزود خارجي قبل قرار (ع)
  المكتوب بشأن المزود والاحتفاظ والمكان والكلفة.

## 9. توسيع عقد Rive

الحركات الحالية تبقى، ونحتاج أن يصمم الـMaster Rig بحيث يقبل لاحقاً:

- locomotion: idle / walk / run / enter / exit.
- hands: receive / hold / carry / give / point / open-document.
- face: read-focus / react-warning / react-positive / talk / blink / look.
- props attachment points: `handL`, `handR`, `documentAnchor`, `uiTarget`.
- انتقال action إلى action من دون قفزة، وإمكانية إلغاء المشهد عند navigation.

الورقة نفسها ليست رسماً ثابتاً داخل Rive: Rive يحمل prop/anchor فقط، وReact
يعرض المحتوى العربي والتفاصيل والصلاحيات.

## 10. تعديل الـSpike قبل الإنتاج

الـSpike الأول لا يكتفي بـidle وwave. يثبت قصة واحدة end-to-end ببيانات وهمية
وخارج الإنتاج:

1. نافذتان تجريبيتان: «المراقب» و«الموظف».
2. زر خصم تجريبي لا يغير قاعدة الإنتاج.
3. خروج حامل الورقة من النافذة الأولى.
4. دخولها في الثانية وتسليمها وفتحها وإظهار النص.
5. قطع الاتصال/إعادة التحميل ثم استئناف القصة دون تكرار.
6. reduced-motion يعرض نفس المعنى بلا ركض أو حركة طويلة.
7. تسجيل القياسات المتفق عليها في `02-decision.md`.

## 11. تقسيم المسؤولية بعد توسيع الرؤية

- **(ع):** يقبل القصة والسلوك والشكل ودرجة مطابقة الوجه، ويرتب أولوية الأفكار.
- **(م):** يكتب storyboards، لغة الحركة، مواضع الواجهة، مراجعة Rive، النصوص
  المرئية، الوصولية، واختبار أن القصة مفهومة وليست مزعجة.
- **(ز):** يراجع الموجود، يصمم event/story runtime والتوصيل والحفظ والصلاحيات،
  ويربط actions بمدخلات Rive مع القياس والاختبارات.
- **المصممة:** تبني الفن والـrig والحركات والattachment points طبق العقد، ولا
  تضع منطق أعمال داخل الملف.

## 12. بوابة البدء

قبل كتابة محرك عام، يرد (ز) على ثلاث نقاط:

1. ما الموجود حالياً الذي نعيد استعماله للأحداث والتوصيل والـInbox؟
2. هل SSE أنسب للبنية الحالية أم WebSocket، ولماذا؟
3. ما أصغر schema يضمن idempotency وcheckpoints وacknowledgement بلا تضخيم؟

بعد جوابه نكتب storyboard تقني لسـيناريو الخصم وننفذ Spike واحداً. نجاح المشهد
هو الذي يثبت المعمارية؛ بعدها نضيف القصص كبيانات/تعريفات، لا ككتل كود مكررة.

— صاغها (م) من رؤية (ع)

# المرحلة 04 — تدقيق طبقة الأمان الثانية

**الكود المدقَّق:** `prod` عند `5fe3a46` (٦ أيلول ٢٠٢٦).
**النطاق:** missions · solar · GPS · vehicles/vehicle bookings/vehicle missions ·
suppliers · products · dashboard summary/today pulse.

هذا تشخيص فقط. لم أغيّر أي handler أو middleware، وطبّقت التقسيم المتفق عليه:
عام مقصود، ملكية داخل المعالج، ومكشوف فعلاً. الحكم مبني على الراوت والمعالج
والشاشة التي تستعمله، لا على اسم الراوت وحده.

## خلاصة قابلة للتنفيذ

### أولوية عالية — مكشوف فعلاً

| المسار | الموجود | الدليل من الواجهة/المعالج | الحكم المقترح |
|---|---|---|---|
| `GET /api/missions` | `requireAuth` فقط؛ `MissionHandler.List` يقبل `leaderId` و`employeeId` من query بلا تحقق | `MissionsPage` يستعمل القائمة الشاملة فقط للإداري/HR/المراقب/`monitoring`، والموظف العادي يستعمل `/missions/my/{employeeId}` | أضف حارس تتبع المهام/المراقبة للقائمة الشاملة |
| `GET /api/missions/monitor/live` | يرجع لوحة متابعة الشركة بلا تحقق داخل المعالج | لا يوجد مستدعٍ حالي بالواجهة؛ الاسم والبيانات للمراقبة | حارس `monitoring`/`mission_tracking` أو الدور المناسب قبل إحيائه بالواجهة |
| `GET /api/missions/reports/performance` | تقرير أداء شامل بلا ملكية | لا يوجد مستدعٍ حالي بالواجهة | حارس إداري/مراقبة، ولا يفتح لمجرد تسجيل الدخول |
| `GET /api/missions/{id}` | يرجع المهمة بالمعرّف بلا فحص عضو/ليدر | الموظف العادي عنده مسار self مستقل، لذلك كشف مهمة أخرى بالـID ليس ضرورياً لصفحته | فحص: عضو/ليدر المهمة أو صلاحية شاملة؛ لا تضع حارساً شاملاً يكسر تفاصيل مهمة الموظف نفسه |
| `GET /api/solar/stats` | مجاميع مخزن/منظومات لكل مسجل | `SolarPage` تحمّله للجميع رغم أن التعديل فقط لـ`solar_system` | حارس قراءة Solar أو `solar_system` إذا لا توجد حاجة ميدانية مثبتة للمجاميع |
| `GET /api/solar/low-stock` | يكشف نواقص المخزن لكل مسجل | معلومة تشغيلية للمخزن وليست مواصفة يحتاجها الفني | `solar_system` أو صلاحية متابعة المخزن المناسبة |
| `GET /api/solar/installations` | يرجع تركيبات الزبائن بلا تضييق | `SolarPage` وحدها تستعمله؛ البيع وعرض السعر يحتاجان systems لا installations | `solar_system`؛ هذا ليس ضمن «قراءة المواصفات مفتوحة للفني» |
| `GET /api/gps/settings` | إعدادات/أسعار GPS كاملة لكل مسجل، والمعالج بلا تضييق | لا يوجد مستدعٍ حالي ظاهر بالواجهة؛ الكتابة مقيدة بـ`requireGpsAdmin` | اجعل القراءة `requireGpsAdmin` أو حارس GPS محدداً إذا احتاجتها شاشة مثبتة |
| `GET /api/vehicles/{id}/documents` و`.../photos` | `requireAuth` فقط، بينما إنشاء/حذف نفس المورد `requireVehicleMgmt` | لا يوجد مستدعٍ حالي من صفحات الواجهة؛ الملف الكامل للسيارة لا تحتاجه شاشة اختيار المركبة | `requireVehicleMgmt` ما لم يظهر مستهلك ميداني محدد |
| `GET /api/vehicle-missions/{id}` | يرجع مهمة مركبة كاملة بلا فحص السائق أو الإدارة | لا يوجد مستدعٍ حالي؛ القائمة الشاملة نفسها مقيدة بـ`requireVehicleMgmt` | السائق صاحب المهمة أو `requireVehicleMgmt` |
| `GET /api/vehicle-bookings` | الفلاتر (`requestedById`) من المستخدم، و`List` يمررها بلا ملكية | لا يوجد مستدعٍ حالي بالواجهة؛ الإنشاء/القرار/الإلغاء كلها إدارة مركبات | ضيّق لطلبات صاحب الجلسة افتراضياً، والشامل فقط لـ`vehicle_management` |

### يحتاج قرار نطاق قبل وضع الحارس

| المسار | سبب عدم القفز إلى حارس واحد |
|---|---|
| `GET /api/gps/renewals` | تستعمله شاشة الموظف GPS وشاشة الطلب وشاشة المراجعة. المعالج يرجع الجميع، بينما بعض المستهلكين قد يحتاجون «طلبي/الخدمة التي أتابعها» فقط. الصحيح endpoint شامل محمي + endpoint self/scoped، لا منع كل الشاشات. |
| `GET /api/gps/maintenance` | نفس مشكلة التجديدات: شاشة الطلب والمراجعة والموظف تشترك بقائمة شاملة. يلزم تعريف الملكية/الخدمة داخل handler قبل الحارس. |
| `GET /api/suppliers` | صفحة الموردين تحتاج `suppliers_management`، لكن Procurement وProductRequests تحتاجان خيارات الموردين أيضاً. القائمة الحالية تكشف تفاصيل أوسع من `getSupplierOptions` المطلوبة. الأفضل `/suppliers/options` محدود الحقول بصلاحيات المشتريات، والقائمة الكاملة بـ`suppliers_management`. |
| `GET /api/suppliers/specialties` | كتالوگ مساعد لصفحة الموردين؛ يمكن إبقاؤه عاماً للمسجلين إذا لا يحتوي معلومات حساسة، أو ربطه بنفس حارس الموردين للاتساق. |

### عام مقصود أو مشترك — لا يُسد آلياً

| المسار | السبب |
|---|---|
| `GET /api/missions/my/{employeeId}` | فيه `requireSelfOrSupervisor` داخل المعالج؛ ملكية فعلية وليست ثغرة `requireAuth`. |
| `GET /api/solar/components` و`GET /api/solar/systems[/{id}]` | تعليق الكود يثبت أن قراءة المواصفات مطلوبة للفني؛ `SalesBooking` و`QuotationNew` يحتاجان systems. عمليات التعديل والتجهيز محمية بـ`requireSolar`. |
| `GET /api/gps/stats` | مجاميع تستعملها Dashboard العامة وGpsDashboard؛ لا توجد صفوف عملاء في الاستجابة. يبقى عاماً ما دامت الحقول مجاميع غير حساسة فقط. |
| `GET /api/vehicles/options` | قائمة مبسطة لازمة لـBookingsList وCoordinator؛ تعليق الراوت يثبت أنها بلا صلاحية إدارة أسطول قصداً. |
| `GET /api/products` | مشترك بين Coordinator وQuotationNew وصفحة المنتجات. عمليات التعديل محمية منفصلة؛ لا نكسر البيع/التنسيق بحارس إدارة المنتجات. |
| `GET /api/dashboard/summary` | أربع عدادات فقط (موظفون/عملاء/حجوزات/أجهزة)، بلا أسماء أو مبالغ. عام للمسجلين ما دام العقد لا يتوسع بصمت. |
| `GET /api/dashboard/today-pulse` | مجاميع بلا بيانات زبائن أو مبالغ، والكود يصرّح أن `requireAuth` مقصود. الواجهة تعرضها للإداري/HR/`coordinator` لكن فتح الـAPI لا يكشف صفوفاً. |

## ترتيب التنفيذ الآمن المقترح لـ(ز)

1. ابدأ بالمسارات التي لا يملك لها frontend مستدعياً حالياً:
   mission live/performance، GPS settings، vehicle documents/photos، vehicle mission get.
2. افصل Solar إلى قراءة مواصفات عامة مقابل مخزن/تركيبات محمية.
3. أصلح `missions/{id}` وvehicle bookings بملكية داخل المعالج، لا بحارس يسد
   الموظف عن سجله.
4. قبل GPS renewals/maintenance والموردين، ابنِ endpoint محدود/self ثم انقل
   الشاشات؛ وضع الحارس أولاً سيكسر شاشات تعمل اليوم.
5. أضف اختبارات 403 + self-access + الدور/الصلاحية المسموحة لكل تغيير.

## تنبيه منهجي

قفل الرابط في `navTree` أو `App.tsx` ليس حماية. بالمقابل، وجود `requireAuth`
وحده ليس ثغرة تلقائياً: `missions/my` مثال ملكية صحيحة داخل handler، وSolar
components/systems وvehicle options أمثلة قراءة مشتركة مقصودة.

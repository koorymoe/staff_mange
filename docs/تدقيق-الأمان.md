# تدقيق أمني — نظام شركة الأماني

> ملف مرجعي للمراجعة الأمنية. صالح للمشاركة مع مدقّق خارجي أو أداة ذكاء
> اصطناعي ثانية لأخذ رأي مستقل. **ما بيه أي كلمة سر ولا مفتاح ولا رابط داخلي.**

## ١. وصف النظام (للمراجع الخارجي)

| البند | التفصيل |
|---|---|
| الباك اند | Go 1.x — `net/http` + `sqlx` (بدون ORM) |
| قاعدة البيانات | PostgreSQL 16 |
| الواجهة | React + TypeScript + Vite |
| المصادقة | JWT (HS256) بصلاحية ١٢ ساعة، السر من متغير بيئة |
| كلمات السر | bcrypt (DefaultCost) |
| النشر | خلف nginx على نفس الجهاز |
| عدد المسارات (endpoints) | ~635 |

نموذج الصلاحيات: دور وظيفي (`role`) + صلاحيات مخصصة (`Permission`) تُمنح
لكل موظف. `OWNER` و`ADMIN` يتخطون كل القيود.

## ٢. ثغرات انلقت وانصلحت (بتاريخ هذا الملف)

| # | الثغرة | الخطورة | الحالة |
|---|---|---|---|
| ١ | `GET /api/projects` كان يرجّع **كل** مشاريع الشركة لأي موظف مسجّل دخول. الواجهة تخفي الصفحة بس الـAPI مفتوح. | 🔴 عالية | ✅ انصلحت — الي ما عنده صلاحية يشوف بس المشاريع الموجّهة له، و`GET /api/projects/{id}` يرجّع 403 |
| ٢ | حد محاولات الدخول يعتمد ترويسة `X-Forwarded-For` الي **يكتبها العميل**. المهاجم يغيّرها بكل طلب فيتجاوز الحد بالكامل (تخمين كلمات سر بلا سقف). | 🔴 عالية | ✅ انصلحت — ما ننثق بالترويسة إلا من بروكسي محلي (loopback) |
| ٣ | خريطة تتبّع محاولات الدخول ما تنظّف نفسها — تكبر بلا حد مع كل IP جديد (استنزاف ذاكرة / DoS). | 🟠 متوسطة | ✅ انصلحت — تنظيف دوري عند ١٠٬٠٠٠ عنوان |
| ٤ | ترويسات الحماية القياسية مفقودة كلياً. | 🟠 متوسطة | ✅ انضافت — `nosniff`، `X-Frame-Options: DENY`، `HSTS`، `Referrer-Policy`، `Permissions-Policy`، `COOP` |
| ٥ | `ParseToken` ما يثبّت خوارزمية التوقيع. | 🟡 واطية | ✅ انصلحت — `WithValidMethods(["HS256"])` |
| ٦ | ١٢ مسار كتابة محمي بـ`requireAuth` بس (GPS، VIP، الكشوفات، المهام، تقييم الموردين، حجوزات/مهام المركبات، تقارير دراسات الخدمات). | 🟠 متوسطة | ✅ انقفلت بصلاحياتها الصحيحة |

## ٣. تحصينات مضافة

- **حظر تلقائي**: ٣ محاولات كلمة سر خاطئة → حظر. أي محاولة وصول لعملية غير
  مخوّلة → حظر فوري. ما ينفك إلا بيد المالك. `OWNER`/`ADMIN` مستثنون عمداً
  (منع قفل النظام على نفسه).
- **سجل أحداث أمني** (`SecurityEvent`): دخول فاشل · دخول لحساب محظور · حظر ·
  فك حظر · وصول غير مخوّل · **تغيير صلاحيات** (منو غيّر لمنو ومتى ومن أي IP).
- **حد حجم الطلب** ٢٥ ميغا · **مهلات السيرفر** مضبوطة (Slowloris).

## ٤. ⚠️ الي لسه مفتوح — يحتاج مراجعة

### أ) مسارات محمية بـ`requireAuth` فقط

بعد إصلاحات اليوم بقت **~١١٤** مسار. أغلبها مقصود (الموظف يسجّل حضوره،
يقرأ إشعاراته، يغيّر كلمة سره)، بس التالية تحتاج قرار:

**كتابة — يحتاج تدقيق ملكية (IDOR محتمل):**
```
PUT  /api/bookings/{id}/complete        ← أي موظف يقدر "ينهي" حجز مو إله؟
PUT  /api/bookings/{id}/arrived
PUT  /api/bookings/{id}/start
PUT  /api/bookings/{id}/materials-ready
PUT  /api/bookings/{id}/schedule
PUT  /api/inventory/requests/{id}/return
PUT  /api/cart/{id}    ·   DELETE /api/cart/{id}
POST /api/expenses     ← لازم ينحصر بمصاريف الموظف نفسه
POST /api/procurement
POST /api/bookings
```
**السؤال للمراجع:** هل يكفي `requireAuth` مع تحقق ملكية داخل الهاندلر، لو
لازم صلاحية صريحة؟ حالياً **ماكو تحقق ملكية** بأغلبها.

**قراءة — تسريب بيانات محتمل:**
```
GET /api/employees      ← يرجّع حقل الراتب لأي موظف مسجّل دخول
GET /api/permissions    ← قائمة أسماء الصلاحيات مكشوفة للكل
GET /api/customers      ← بيانات الزبائن كاملة
GET /api/bookings
```

### ب) نقاط بنيوية

| البند | الوصف |
|---|---|
| تخزين الملفات | الصور والوثائق مخزونة **base64 داخل قاعدة البيانات**. يكبّر القاعدة ويبطّي الاستعلامات. الحل: تخزين خارجي برفع موقّع مسبقاً (presigned). |
| مكتبات npm | ٣ ثغرات مصنّفة "عالية" لسه ما انحدّثت. |
| صلاحية الـJWT | ١٢ ساعة بدون آلية إبطال (revoke). موظف انفصل يضل توكنه شغّال لحد ما ينتهي. |
| سياسة كلمة السر | الحد الأدنى ٦ أحرف فقط، بدون شرط تعقيد. |
| المصادقة الثنائية (2FA) | غير موجودة. |

## ٥. أسئلة نريد رأياً مستقلاً بيها

1. الحظر التلقائي عند **أول** محاولة وصول غير مخوّلة — هل هو صارم زيادة؟ خطأ
   بالواجهة ممكن يحظر موظفين أبرياء. البديل: حظر بعد ٣ محاولات.
2. حماية طبقة الوصول للبيانات (ownership) — الأفضل ميدل وير عام، لو تحقق
   داخل كل هاندلر؟
3. مع JWT بدون revoke — نضيف قائمة إبطال (blacklist)، لو نقصّر المدة ونضيف
   refresh token؟
4. `OWNER`/`ADMIN` مستثنون من الحظر التلقائي — هل هذا قرار صحيح، لو نضيف
   حماية بديلة إلهم (مثلاً تنبيه فوري بدل الحظر)؟
5. الحظر مبني على `status='SUSPENDED'` + `lockedAt` — هل ينفع نميّز الإيقاف
   الإداري عن الحظر الأمني بهالشكل، لو نحتاج حالة مستقلة؟

## ٦. الي انفحص وطلع سليم

| الفحص | النتيجة |
|---|---|
| SQL Injection | ✅ كل الاستعلامات بمعاملات. `fmt.Sprintf` مستخدمة بس لأرقام الـplaceholders (`$1`, `$2`) مو للقيم |
| XSS | ✅ ماكو `dangerouslySetInnerHTML` ولا `innerHTML=` بالمشروع كله |
| تسريب كلمات السر | ✅ `json:"-"` — ما تنرجع بأي رد |
| تخزين كلمات السر | ✅ bcrypt |
| CORS | ✅ مقيّد بقائمة أصول محددة |
| أسرار مكتوبة بالكود | ✅ ماكو — كلها من متغيرات البيئة، والسيرفر يرفض يشتغل بدون `JWT_SECRET` قوي |
| حجم الطلبات | ✅ ٢٥ ميغا |
| مهلات السيرفر | ✅ Read/Write/Idle مضبوطة |
